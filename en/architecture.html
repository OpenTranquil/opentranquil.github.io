Architecture

A system organized by privilege levels, object authorization and service boundaries.

TranquilOS turns ARMv8-A exception levels into an architectural language: EL2 runs a Type-1 hypervisor, EL1 is a capability microkernel that only dispatches objects and schedules, and EL0 carries everything from SystemDaemon to graphical apps. Layers interact only through capability calls, migrating-thread IPC and shared memory.

Blueprint

Three runtime layers — each does only its own job.

Boot hands off down the chain EL2 → EL1 → EL0; at runtime, requests sink back down through capability calls. Components inside EL0 talk only over IPC + SHM.

Capability System

Every kernel object is reached through a capability.

Each process owns a CNode holding references to the kernel objects it may access. The CNode is built on a directory array — array-speed indexing with dynamic-array growth, expanding without copying existing slots. A capability reference (cref) is a 64-bit value: upper 32 bits cnode ID, lower 32 bits slot index; the root CNode has ID 1. The kernel checks object type and a 32-bit rights mask before every method dispatch.

Upcall is the reverse path: the kernel hands syscalls it cannot handle, page faults and similar events to a handler registered by the process — policy stays in userspace.

IPC Model

Migrating-thread IPC: cross-process calls that behave like function calls.

Traditional IPC only responds once the server thread gets scheduled onto a CPU — latency is nondeterministic. TranquilOS synchronous IPC migrates the caller's execution context into the callee's address space: IPC does not depend on scheduler behavior, so it is faster and predictable.

MIGRATING THREAD

Switch execution context, not scheduling state

Thanks to the scontext/xcontext split, the kernel constructs the target process's execute_context_s on IPC: arguments go into x0–x7 per the AAPCS, the entry address into pc, and a trampoline address into lr — when the handler returns, the trampoline issues a REPLY call that switches back to the caller. Scheduling metadata stays under the scheduler's control the whole time, so even heavy IPC never starves other threads.

ENDPOINT & POOL

Single-threaded endpoints and elastic pools

An endpoint is single-threaded — one handler thread per endpoint. An endpoint pool load-balances across pre-allocated endpoints for multi-threaded services (elastic IPC), while the client API stays identical in both modes. A kernel name service lives at cref 0x1: services register with sys_register_service(), clients look them up with sys_get_service().

01alloc_shm

The client allocates shared memory from SystemDaemon.

02map & copy

Map the SHM and write the request data.

03ipc call

Issue the IPC call, passing the SHM handle as an argument.

04get_shm

The service maps the same SHM region.

05process

Operate directly on the shared data — zero copy.

06reply & free

Reply; the client frees the SHM.

SHM is the only data channel between processes — TranquilOS has no message-copying IPC. All bulk data moves through shared memory; IPC argument slots carry handles and scalars only.

Scheduler

Scheduling and execution are two data structures.

The traditional TCB is split into a schedule_context_s (scheduling entity) and an execute_context_s (execution entity). Per-CPU schedulers manipulate only scheduling metadata; register state is constructed on real context switches. Under SMP each CPU runs a local scheduler with cross-core load balancing, and CFS is plugged in as a loadable kernel module.

SystemDaemon & Memory

The kernel keeps only a boot allocator — memory policy lives in EL0.

The microkernel keeps just a boot-time allocator for itself and SystemDaemon startup. SystemDaemon is a privileged EL0 process linked at 0x43080000 that issues capcalls directly, exposing four managers as singleton components: procmgr (processes/threads, ELF loading), memmgr (buddy physical-page allocation, SHM), ipcmgr (endpoints/pools, name service, capability cloning) and virtmgr (virtual machines).

Boot

Boot: leveled initcalls, fixed image layout.

The linker places initialization functions into dedicated sections for levels LV0–LV7, and the kernel runs them in order; the bootloader decides whether to start the hypervisor first or enter the kernel directly, based on CurrentEL.

Service ABI

Every service shares one skeleton; interfaces are written in IDL and code-generated.

All framework services follow the same structure: main.c initializes and registers, service/service.c dispatches by method number, and client/ is a thin IPC wrapper. The IDL generator emits five files — types, client and service — with ABI version and size validation.

// service.c — the same dispatch pattern in every service
static handler_fn handlers[] = {
  [IPC_SERVICE_FUNCTION_CREATE] = handler_create,
  [IPC_SERVICE_FUNCTION_DESTROY] = handler_destroy,
  // ...
};

IPC_ENDPOINT void service_entry(
    uint64_t cref, uint64_t method,
    uint64_t a1, uint64_t a2, uint64_t a3) {
  if (method < HANDLERS_COUNT && handlers[method])
    OSIpcEndPointPoolReply(handlers[method](a1, a2, a3));
  else
    OSIpcEndPointPoolReply(0);
}
// statemgr_ipc.idl
service statemgr_ipc {
    id = 0x9;

    struct query  { version = 1; char key[64]; };
    struct result { version = 1; uint32_t found; };

    uint64_t get(persistent in query *request,
                 persistent out result *response) id = 0x1;
};

persistent parameters let the SHM buffer of a fixed-size control struct be reused across calls: lazily allocated by the client, mapped once by the server — every call still performs a real IPC. Transport structs must declare a version; the generator adds abi_size / abi_version fields validated by the server. Pointer fields are not allowed in transport structs — variable-length data passes an explicit SHM handle and length.
