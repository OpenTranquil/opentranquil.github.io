AArch64 · Object-Capability · Userspace Services

A microkernel operating system implemented end to end, from bootloader to graphical desktop.

TranquilOS uses capabilities as its single authorization model: the EL1 microkernel only handles scheduling, IPC, exceptions and object dispatch, while processes, memory, filesystems, networking, window composition and every other system capability live in clearly bounded userspace services — a complete system spanning an EL2 Type-1 hypervisor to 14+ graphical applications.

Design Pillars

Three decisions that shape the whole system.

TranquilOS is not a kernel toy — it is a full validation of the "microkernel + capability authorization + userspace services" combination on AArch64.

CAPABILITY

Object-based authorization, no implicit privilege

Processes hold capability slots in a CNode, not global privileges. Accessing a VSpace, Endpoint, Timer, Futex or IRQ requires a typed capability, and the rights mask is checked before every method dispatch.

USERSPACE

Userspace is the body of the system

Process management, physical memory allocation and the IPC namespace belong to the privileged EL0 SystemDaemon; windows, files, networking, devices and app lifecycle are independent services. Failure domains map one-to-one to responsibilities.

END-TO-END

A complete implementation path

From bootloader, DTB, hypervisor and kernel to zygote, framework services and graphical apps, every stage has a defined image location, initialization duty and handoff target — all reproducible from source.

Boot Chain

Six stages, each with a single job.

01Bootloader

Early platform init, device-tree parsing and image loading; enters the EL1 kernel directly or starts the EL2 hypervisor first, depending on CPU CurrentEL.

02Hypervisor

EL2 Type-1: stage-2 translation, VM/VCPU/PCPU lifecycle, vGIC, vTimer, vPMU and the hypcall interface.

03Microkernel

EL1: capability object dispatch, migrating-thread IPC, SMP scheduling, IRQ, timers, futex, upcalls, modules and low-level drivers.

04SystemDaemon

Privileged EL0 process: process/thread creation, ELF loading, physical page allocation, SHM mapping, endpoint namespace, VM management.

05Framework

init → zygote brings up windowmgr, fsmgr, netmgr, devmgr, appmgr and the other services, all connected over SHM+IPC.

06Applications

systemui, launcher, settings, files, monitor, music, whiteboard, nes, ai and more run on the same service boundaries.

Kernel Decisions

Core mechanisms are designed around isolation, call latency and interface maintainability.

CAP

Object-capability

An seL4-inspired object-capability model. A cref is a 64-bit reference: upper 32 bits cnode ID, lower 32 bits slot. The CNode uses a directory array for linear indexing with copy-free growth.

IPC

Migrating-thread IPC

Synchronous calls don't wake a server thread through a message queue — the caller's execution context migrates into the callee's address space. Endpoint pools scale server concurrency.

SMP

Split schedule/execute contexts

scontext and xcontext are separate: per-CPU schedulers only touch scheduling metadata; register state is only constructed on real context switches. CFS ships as a loadable kernel module.

IDL

Generated service bindings

Interfaces are described in .idl files; the generator emits client wrappers, server dispatch, transport structs and ABI checks. Persistent SHM parameters reuse mappings for fixed control structs.

Coverage

The implementation covers kernel, virtualization, services, graphics, networking and tooling.

Kernel core

Exception model, MMU, SMP per-CPU scheduling, capability dispatch, migrating-thread IPC, fastcall, upcall, futex, IRQ, high-precision timers, module system, perf tracing.

Virtualization

EL2 Type-1 hypervisor: stage-2 page tables, VM/VCPU/PCPU lifecycle, vGIC, vTimer, vPMU, hypcall.

System services

Four SystemDaemon components (procmgr/memmgr/ipcmgr/virtmgr) plus framework services: windowmgr, fsmgr, netmgr, devmgr, appmgr, audiomgr, fontmgr, statemgr, timemgr, agentmgr and more.

Graphics & apps

An 800×480 landscape canvas with LVGL + FreeType + PortableGL; 14+ user applications run on top of the window compositor.

Storage & network

VFS over rootfs, ext2, FAT32, procfs and sysfs; lwIP TCP/IP stack with mbedTLS for HTTPS.

Tooling

GN/Ninja builds every ELF and image; the IDL generator eliminates service glue code; four platform scripts cover QEMU and real Raspberry Pi hardware.

Run It

From source to a bootable image — one command.

With the aarch64-elf cross toolchain installed, the run script performs the GN/Ninja build, assembles boot.img and system.img, and launches QEMU with 4-core SMP, 2 GB RAM, VirtIO devices and a ramfb display.
