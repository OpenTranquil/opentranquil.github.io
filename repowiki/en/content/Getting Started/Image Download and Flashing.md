## Scope

This document explains how to use the prebuilt TranquilOS images distributed through the website. The images target two environments: the QEMU virt virtual platform and Raspberry Pi Compute Module 4. Use prebuilt images for quick validation of the boot chain, graphical session, userspace services, and application layer. Use a source build when changing the kernel, system services, drivers, or applications.

## Image List

| Image | Target platform | Typical use |
| --- | --- | --- |

| `tranquil-cm4.img` | Raspberry Pi Compute Module 4 | Validate CM4 boot, HDMI output, serial logs, eMMC/SD flashing paths, and peripheral initialization on real hardware. |

## Disk Structure

Both images are raw disk images, not standalone kernels or boot containers. The QEMU virt image is generated by `platform/QemuVirt/scripts/make_all_img.sh`; the CM4 image is generated by `platform/CM4/scripts/make_all_img.sh`. Both use the same three-partition model:

| Partition | Filesystem | Content |
| --- | --- | --- |
| P1 | FAT32 | `boot.img`; the CM4 image also includes firmware and `bcm2711-rpi-cm4.dtb`. |
| P2 | ext2 | `system.img`, containing zygote, framework services, system UI, and application ELFs. |
| P3 | ext2 | `user.img`, containing user-data templates, music, photos, NES ROMs, and AI configuration. |

## Integrity Verification

Image files are large and can be truncated during download, copy, or flashing. Generate SHA-256 digests in the distribution directory and verify them again on the target host before writing media.

```bash
shasum -a 256 downloads/tranquil-virt.img
shasum -a 256 downloads/tranquil-cm4.img
```

Formal releases should publish `.sha256` files and record the image generation time, source commit, target platform, and validated boot method.

## Booting QEMU virt with `tranquil-virt.img`

Prefer the run script in the kernel repository. `run_qemu_virt.sh` builds the project, creates `boot.img`, `system.img`, and `user.img`, assembles `tranquil-virt.img`, and starts QEMU.

```bash
cd /Users/neo/kernel
source env_setup.sh
./run_qemu_virt.sh
```

The current script attaches `out/tranquil-virt.img` as a raw VirtIO block device:

```bash
-drive if=none,format=raw,file=./out/tranquil-virt.img,id=disk
-device virtio-blk-device,drive=disk,bus=virtio-mmio-bus.3
```

If you already have `tranquil-virt.img`, place it under the repository `out/` directory or the location expected by the scripts, then reuse the QEMU boot script. If writing QEMU arguments manually, keep the machine model, CPU, memory, device tree, display backend, VirtIO devices, and serial parameters aligned with `platform/QemuVirt/scripts/run.sh`. Mismatched parameters can cause missing graphics output, unavailable block devices, or early boot failures.

## Flashing `tranquil-cm4.img`

Confirm the target device before flashing. `dd` overwrites the target disk. Selecting the wrong device can destroy data on the host or on another external drive.

### Automated CM4 Flow

The repository `run_board_cm4.sh` currently calls `platform/CM4/scripts/flash.sh`. That script performs:

1. Calls `make_all_img.sh` to build all ELFs, `boot.img`, `system.img`, `user.img`, and `tranquil-cm4.img`.
2. Runs `platform/CM4/tools/rpi/rpiboot`.
3. Uses `diskutil` to find the newly attached external USB removable device.
4. Writes `out/tranquil-cm4.img` through the raw `/dev/rdiskN` path.
5. Unmounts and ejects the device after writing.

```bash
cd /Users/neo/kernel
source env_setup.sh
./run_board_cm4.sh
```

### Manual macOS Write

1. Insert the SD card, or expose CM4 eMMC through mass-storage mode.
2. Use `diskutil list` to identify the target disk number.

```bash
diskutil list
```

3. Unmount the whole disk and write the image. Replace `diskN` with the actual disk number.

```bash
diskutil unmountDisk /dev/diskN
sudo dd if=downloads/tranquil-cm4.img of=/dev/rdiskN bs=4m status=progress conv=sync
sync
diskutil eject /dev/diskN
```

### Manual Linux Write

1. Insert the target media and use `lsblk` or `dmesg` to identify the device name.

```bash
lsblk
```

2. Replace `/dev/sdX` with the actual whole-disk device. Do not write to a partition node such as `/dev/sdX1`.

```bash
sudo umount /dev/sdX*
sudo dd if=downloads/tranquil-cm4.img of=/dev/sdX bs=4M status=progress conv=fsync
sync
```

For eMMC, NVMe, or SD controllers, the device name may be `/dev/mmcblk0`, `/dev/nvme0n1`, or another form. Use the whole-disk device shown by `lsblk`.

## Post-Boot Validation

After boot, validate the system in this order:

1. Serial logs: confirm that the bootloader, hypervisor, kernel, and SystemDaemon complete initialization.
2. Kernel objects: confirm capability root, scheduler, IRQ/timer, and basic driver registration.
3. Display output: QEMU virt and Pi4/CM4 graphical targets should show the 800x480 system canvas.
4. Userspace services: confirm FsMgr, DevMgr, WindowMgr, AppMgr, and related services register successfully.
5. Application launch: confirm launcher, settings, files, or monitor can start.

If the system does not boot, first check image integrity, whether the target was a whole-disk device, the CM4 boot-mode jumper, serial wiring, and QEMU arguments.
