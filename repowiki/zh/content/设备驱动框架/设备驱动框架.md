## 定位

TranquilOS 的设备体系分为两层：内核保留早期设备树解析、关键中断/时钟/控制台驱动和少量硬件抽象；用户态 `Devmgr` 承接设备枚举、设备服务化和更高层管理。这样的划分符合微内核设计：硬件可用性和调度基础由内核保障，设备策略和服务接口尽量放在 EL0。

## 内核设备子系统

`sys/kernel/device` 提供统一的设备注册和设备树读取能力。驱动通常通过 compatible 字符串匹配 DTB 节点，读取寄存器地址、IRQ、属性和平台配置，再把自身注册到内核对应子系统。

核心接口集中在：

- `device_tree.c`：DTB 初始化、节点遍历、compatible 查询、属性读取、地址解析。
- `device.c`：设备描述符注册和 probe 入口。
- `initcall.h`：按初始化阶段组织驱动加载顺序。
- `interrupt/irq_mgr.c` 与 `timer/timer_mgr.c`：把设备中断和硬件定时器纳入内核调度路径。

## 已纳入构建的驱动

当前 `sys/kernel/BUILD.gn` 纳入的驱动包括：

| 类别 | 驱动 |
| --- | --- |
| 串口与控制台 | `arm-uart/pl011.c`、`kmsg/kmsg_console.c` |
| 中断控制器 | `arm-gic/gicv2.c`、`arm-gic/gicv3.c` |
| 时钟与 RTC | `arm-timer/generic_timer.c`、`arm-rtc/pl031.c` |
| 电源与启动 | `arm-psci/psci.c`、`spin-table/spin_table.c`、`arm-watchdog/sp805.c` |
| 性能与缓存 | `arm-pmu/pmuv3.c`、`arm-pmu/spe.c`、`arm-cache/pl310.c` |
| 图形与 DMA | `arm-mali/*`、`arm-dma/pl080.c` |
| 虚拟化桥接 | `hvdriver/hypervisor.c` |

这些驱动并不等价于完整 Linux 风格驱动栈。它们主要服务于内核启动、控制台输出、计时、中断、平台控制和后续用户态服务的资源授权。

## 用户态 Devmgr

`sys/uapps/core/devmgr` 是设备管理的用户态基础服务。它与内核设备能力、文件系统服务和框架服务配合，把底层设备转换为用户态可访问的服务接口。对于微内核系统而言，`Devmgr` 是把“硬件事实”转换为“系统资源”的关键层。

典型职责包括：

- 接收和维护设备枚举结果。
- 为设备节点建立用户态访问路径。
- 与 `Fsmgr` 协作，把设备暴露为文件或服务端点。
- 为 OS framework 中的显示、输入、音频、网络等服务提供设备基础。

## 设备树与平台

平台资源由 `platform/*/dts` 和 `platform/*/dtb` 描述。当前主要平台包括：

- `QemuVirt`：用于本地虚拟化调试，DTB 为 `platform/QemuVirt/dtb/virt.dtb`。
- `CM4`：树莓派 Compute Module 4，DTB 为 `platform/CM4/dtb/bcm2711-rpi-cm4.dtb`。
- `Pi3b` / `Pi4b`：树莓派 3B、4B 平台，分别提供独立 DTB、链接脚本和运行脚本。

驱动开发时应优先从 DTB compatible、reg、interrupts 和平台 linker script 入手，确认硬件地址、异常级、MMU 映射和镜像布局是否一致。

## 开发建议

- 新增内核驱动时，把 probe、DTB compatible、初始化阶段和中断注册写清楚。
- 对可以放入用户态的策略逻辑，优先放到 `Devmgr` 或更高层服务，不扩大内核驱动职责。
- 修改平台 DTS 后，需要重新生成或确认对应 DTB，并通过平台脚本重新制作镜像。
- 修改 GIC、timer、console、PSCI 这类关键驱动后，应至少验证 QEMU Virt；涉及树莓派外设时再验证对应板卡镜像。
