## 定位

TranquilOS 当前安全模型主要由微内核对象隔离、Capability 授权、地址空间隔离、IPC/Upcall 边界、用户态服务拆分和可选 EL2 Hypervisor 组成。旧文档中提到的 `trustee/BUILD.gn`、TrustZone 安全世界和 `boot/boot.c` 路径并不是当前主线源码的有效入口；当前仓库的安全边界应以 `sys/kernel`、`sys/virt`、`sys/uapps` 和 `sys/ulibs` 为准。

## 安全边界

| 边界 | 实现位置 | 作用 |
| --- | --- | --- |
| 异常级隔离 | `sys/kernel`、`sys/virt` | EL1 微内核与可选 EL2 Hypervisor 分离高权限机制 |
| 地址空间隔离 | `sys/kernel/mm`、`cap_vspace.c` | 通过 VSpace 和页表控制用户态映射 |
| Capability 授权 | `sys/kernel/capability` | 用 CNode 和 capability reference 代替裸资源句柄 |
| IPC 边界 | `sys/kernel/ipc`、`sys/kernel/systemd/*/idl` | 服务调用必须通过端点和生成 wrapper |
| Upcall 边界 | `sys/kernel/upcall` | 异常、通知和异步事件按端点返回用户态 |
| 中断授权 | `sys/kernel/interrupt`、`cap_irq.c` | 硬件中断经内核对象授权给用户态处理 |
| 服务拆分 | `sys/uapps`、`os/framework` | 设备、文件系统、应用、窗口等策略放在 EL0 服务 |

## Capability 安全模型

系统不依赖全局用户身份来授予内核对象访问权，而是依赖 Capability。一个服务只有在 CNode 中持有相应引用，且权限位允许，才能调用对应对象方法。这样可以实现：

- 最小授权：只传递完成任务需要的能力。
- 权限收敛：子服务无需继承父服务全部权限。
- 对象封装：内核对象不暴露裸指针给用户态。
- 服务隔离：服务间通过 IPC endpoint 和明确 capability 建立关系。

## 内存与执行隔离

地址空间由 `VSpace` 能力管理，执行状态由 `XContext` 和 `SContext` 描述。进程构造、映射、调度加入、异常回调都需要经过内核对象和 Capability 检查。`SystemDaemon` 负责早期内存、进程和 IPC 资源编排，是从内核机制到用户态策略的关键过渡点。

## 虚拟化安全边界

`sys/virt` 提供 EL2 Hypervisor、VM、VCPU、Stage-2 页表和 hypcall 基础。它适合承载必须运行在更高异常级的隔离机制。普通 OS 服务策略不应迁移到 EL2；否则会削弱微内核用户态化的设计目标。

## 开发准则

- 新增内核对象必须定义 capability 类型、方法、权限和失败语义。
- 新增服务接口应通过 IDL/IPC 或明确的 client API 暴露，不应直接共享内部结构。
- 高权限 capability 只能传给确实需要的服务，传递路径应可追踪。
- 修改页表、IPC、Upcall、中断或调度路径后，应执行完整 QEMU Virt 启动验证。
- 涉及 CM4 或真实硬件时，还应检查平台 DTB、链接脚本和镜像布局。
